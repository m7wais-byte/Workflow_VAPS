# Code review: PR #68 (OneDrive pilot + email from bsg@), 27 Nov 2026

**Scope:** the code PR #68 adds on top of `main` (`origin/main...release/rc-68`), about 1,250 lines of application code: `server/onedrive.ts`, `server/mail.ts`, `server/notify.ts`, the new and changed API routes, the OneDrive panel, the email log and migrations 0006–0007.

**Method:** OneDrive and email were each reviewed independently, then I checked every finding below against the code myself. Where a claim depends on Microsoft's behaviour, the Microsoft documentation is cited.

**Not tested:** none of this has run against real Microsoft services. It is a review, not a fix: nothing in the product code has been changed, pending the builder's answer on how changes reach their repository.

The repository's own tests for both parts pass: `tests/onedrive-pilot.test.mjs` 15/15, and the email suite (see below). Those tests use in-memory stand-ins for Microsoft, which is why the findings below are possible at all.

## Summary
The design is careful: secrets stay out of replies and logs, access is limited to the right people, a mail or OneDrive failure never undoes a workflow step, and the same message cannot be queued twice. The problems are in the failure paths, which the stand-ins never exercise, plus two gaps in the setup documents.

**Before the live OneDrive test, fix:**
- **O1:** duplicate copies.
- **O2:** an error status that never clears.
- **O3 / E4:** saves wait for Microsoft.

Then run the O10 checks as part of the test.

**Before the live email test, fix:**
- **E1:** wait up to 2 hours after the mailbox grant, not 1. This is a document fix.
- **E2:** confirm the mailbox's sign-in name.
- **E3 and E5:** two ways a "check Sent Items" or retry can send a second copy.
- **E6:** engineers whose test starts on a later date never get an assignment email.

**Decisions for the builder / VAPS:**
- **O5:** whether switching OneDrive on should copy earlier files.
- **O6:** making the account and tenant settings required.
- **D1:** hiding the deployment check on the live site.

## OneDrive pilot

| # | Severity | Finding | Where |
|---|---|---|---|
| O1 | **Fix before the live test** | **A file can be copied twice ("name 1.csv").** A copy is skipped only when its row is already `ok`, and the upload uses `conflictBehavior=rename`. Nothing claims the row first, and nothing checks whether an earlier attempt already reached OneDrive. So: <br>• A Retry and a job save at the same moment each upload the file. <br>• A 429/5xx or 30 s timeout that arrives after OneDrive stored the file triggers one automatic resend. <br>• If the audit insert fails after the `ok` update, the row is marked `error` and copied again on the next save. <br>Each case leaves a renamed duplicate, which breaks step 4 of the live test ("no duplicate files"). | `server/onedrive.ts:257-287`, `:106` |
| O2 | **Fix before the live test** | **A job's OneDrive error never clears.** Once a folder step fails (for example, OneDrive was disconnected during a save), the job row is set to `error`. Later successful saves return early because the folder IDs are already recorded (`:215`), so nothing resets the status. The panel keeps showing "Needs retry / OneDrive is not connected" after it works again. | `server/onedrive.ts:212-221`, `:298-303` |
| O3 | **Fix before the live test** | **Saves wait for OneDrive (and for email) before replying.** The job, workflow-command, trash and upload routes `await` the OneDrive sync and then the notifications inside the request. Each call can take: <br>• 15 s for the token; <br>• 30 s per Graph call; <br>• plus one resend after a short wait. <br>If Microsoft is slow, a save can hang about a minute per pending file (up to 20). The browser serialises saves (`app/workspace-sync.ts:59`), so that user's later saves queue behind it. A user who leaves mid-save can also cancel the work and feed O1. Usual fix: reply first, then do the copy in `ctx.waitUntil`, with shorter timeouts. | `app/api/jobs/[id]/route.ts:15-17`, `operations/route.ts`, `trash/route.ts`, `app/api/files/route.ts:22,27` |
| O4 | Medium (security/operations) | **Disconnect is not immediate.** Each Worker instance caches the access token in memory and uses it before checking the database status (`:84`). Disconnect clears only the instance that handled the request. Other instances keep copying until their token expires: "60-90 minutes (75 minutes on average)" ([access tokens](https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens)). The optional live-test step "disconnect, then upload" may pass or fail depending on which instance answers. Fix: check the stored status on every use, or keep the cache only a few minutes. | `server/onedrive.ts:81-96`, `:169-172` |
| O5 | Decide | **Uploads are queued for OneDrive even while the pilot is off.** Every job upload, and every scope attachment, is recorded as `pending` in `onedrive_files` regardless of the settings (seen in the local walk: 2 pending rows with the pilot off). Once the pilot is switched on, each job's next save copies up to 20 of those earlier files. That is harmless with sample data, but with real records it means switching OneDrive on copies past files too. Decide whether that is wanted; if not, record rows only while the pilot is on. | `app/api/files/route.ts:26`, `server/onedrive.ts:229-241`, `:295` |
| O6 | Low | **Optional settings weaken the checks.** <br>• If `ONEDRIVE_ACCOUNT` is unset, any account that approves the sign-in is accepted. <br>• If `ONEDRIVE_TENANT_ID` is unset, the code uses `organizations`, which a single-tenant app registration (as ONEDRIVE-PILOT.md asks for) is expected to refuse. <br>Make both required in `oneDriveConfig`. | `server/onedrive.ts:37-42`, `:153-158` |
| O7 | Low | **Sign-in polling can overlap.** The panel polls every 5 s without waiting for the previous call. A slow successful poll and a second poll can race, and the loser writes `not-connected` from its stale row. `pending_interval` is stored but unused, and `slow_down` does not lengthen the interval. | `app/onedrive-panel.tsx:44`, `server/onedrive.ts:~140-151` |
| O8 | Low | **"Never throws" has gaps.** <br>• D1 reads at `:260` and `:305` are outside the `try`. <br>• In the upload route, routing runs after R2 and the `files` row are written, so a D1 error there returns 500 after the original is already stored. <br>• If `ONEDRIVE_TOKEN_KEY` is changed, sign-in polling returns 500, and copies say "could not be reached" instead of "reconnect". | `server/onedrive.ts:260,305,146`, `app/api/files/route.ts:26` |
| O9 | Low | **Trashing a job creates its folders.** The trash and restore route also runs the sync, so trashing a job that was never synced creates `<Job ID>/Sampling` and `<Job ID>/Lab`. | `app/api/jobs/[id]/trash/route.ts` |
| O10 | Check in the live test | **Graph details the stand-ins cannot prove.** <br>• **Same-name upload:** `conflictBehavior=rename` is in the URL, which is where Microsoft says it belongs for PUT ("The default for PUT is replace", [driveItem](https://learn.microsoft.com/en-us/graph/api/resources/driveitem)). Make the test's optional same-name upload mandatory, because a silent overwrite would lose a file. <br>• **Folder creation** sends `conflictBehavior` in the body, as Microsoft's create-folder example does. <br>• **Sharing link:** `btoa()` is fine for normal ASCII links. <br>• **File names:** `safeName` misses trailing dots or spaces and reserved names (for example `desktop.ini`). Such a file stays in `error` and is resent, up to 20 MB, on every save. | `server/onedrive.ts:184,193,250,268` |

**Checked and found correct:**
- **Device code flow:** endpoints and error handling match [Microsoft's device code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-device-code).
- **Refresh tokens:** the new token is stored on every refresh. Two refreshes at once are safe, because Microsoft "doesn't revoke old refresh tokens when used to fetch new access tokens" ([refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens)).
- **Upload size:** a simple upload handles up to 250 MB, so the 20 MB limit is fine ([PUT content](https://learn.microsoft.com/en-us/graph/api/driveitem-put-content)).
- **Folder concurrency:** two saves at once reuse the same folder, with no "<Job ID> 1".
- **Encryption:** AES-GCM with a fresh random IV for each seal.
- **Injection:** job IDs are validated, and file names are encoded.
- **SQL:** all statements use bound values.
- **Access:** the admin routes are MA001-only, with the same-origin check.
- **Secrets:** nothing secret reaches replies or logs.
- **Migrations:** the column names match the code.
- **File routing:** matches ONEDRIVE-PILOT.md.
- **Deleted folders:** a deleted job folder is re-created.

## Email from bsg@visionaps.com

The test file `tests/mail-notifications.test.mjs` passes 10/10. Its Graph stand-in only ever answers 202, 503, 504 or a timeout.

| # | Severity | Finding | Where |
|---|---|---|---|
| E1 | **Fix before the live test** (document) | **The mailbox permission can take up to 2 hours, not 1.** EMAIL-SETUP.md §1d says "up to an hour". Microsoft: "Changes to app permissions are subject to cache maintenance that varies between 30 minutes and 2 hours", and "the test command bypasses this cache" ([RBAC for Applications](https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac)). So `InScope: True` can show while real sends still get 403. Each 403 is logged Failed, and every invitation sent in that window is cancelled. Wait 2 hours after the grant before the test. | `EMAIL-SETUP.md` §1d; `app/api/admin/invitations/route.ts:35-39` |
| E2 | Check in setup | **The mailbox is addressed by its email address.** Graph documents `/users/{id \| userPrincipalName}/sendMail` ([sendMail](https://learn.microsoft.com/en-us/graph/api/user-sendmail)). If bsg@ is a shared mailbox whose sign-in name differs from bsg@visionaps.com, sends may get 404. The sender is fixed in the code, so this cannot be changed by configuration. Add `Get-EXOMailbox bsg@visionaps.com \| fl UserPrincipalName,PrimarySmtpAddress` to step 1a and confirm the two match. | `server/mail.ts:84,115` |
| E3 | **Fix before the live test** | **The "Check Sent Items" step can lead to a second send.** A 202 means "Outlook creates a new message in the sender's Drafts folder". It moves to Sent Items only later, after transport ([send-mail process](https://learn.microsoft.com/en-us/graph/outlook-things-to-know-about-send-mail)), so an unknown-outcome message may not be there yet when MA001 looks. The dialog also says to look around the row's **creation** time, not the last attempt, and several emails can share one subject. Fix: <br>• show the last attempt time; <br>• tell MA001 to wait a few minutes; <br>• put a short unique reference in each subject or body so the right message can be found. | `app/email-log.tsx:43` |
| E4 | **Fix before the live test** (same root cause as O3) | **Emails are sent inside the save request.** After the OneDrive sync, the job and workflow-command routes send each notification in turn, allowing up to 15 s for the token and 20 s for each send, before replying. If the user reloads during a slow run, Cloudflare may cancel the request ("When the client disconnects… tasks associated with that request may be canceled", [limits](https://developers.cloudflare.com/workers/platform/limits/)). Notifications not yet written then leave no log row, and they are never regenerated because the revision has moved on. The save itself is never undone by a mail error, which is correct. Fix: write all outbox rows as `queued` in one batch first, then send them after the reply (`ctx.waitUntil`). | `app/api/jobs/[id]/route.ts:17`, `operations/route.ts`, `server/notify.ts:201-220` |
| E5 | Fix | **A 503 is treated as "not sent" and gets a plain Retry.** The code's comment says 503 means a refusal before processing. Microsoft says only "temporarily unavailable… or overloaded" ([errors](https://learn.microsoft.com/en-us/graph/errors)), so a 503 does not prove the message was not accepted. Treat it like 500/502/504 (Outcome unknown). Treating 429 as Failed is right. | `server/mail.ts:125-126` |
| E6 | **Fix before the live test** | **No assignment email for a test planned to start later.** A test assigned with a future planned start goes to "Coming up", not to the actions list (`app/work-items.ts:183`). The email is sent only when an action newly appears in a saved change, and nothing re-checks on the start date. So the engineer is never emailed about the assignment. Chemistry assignment requires a planned start, so this hits often. | `server/notify.ts:52-60`, `app/work-items.ts:183` |
| E7 | Low (configuration) | **Job drafts can email other job creators.** A saved draft can email every other holder of *Create job* with "Assigned to you: Continue job draft". With the default settings only SALIM holds that permission. | `app/work-items.ts:106` |
| E8 | Low | **One error stops the rest.** A single try/catch covers all recipients of a change, so one error (a D1 failure, or a due value that isn't `yyyy-mm-dd`) skips the remaining recipients without a log row. | `server/notify.ts:89,201` |
| E9 | Low | **Unusable addresses are skipped without a trace.** A client address that fails the format check (for example `a@x.com; b@y.com` or `Name <a@x.com>`), or a missing staff email, writes no row. MA001 cannot see why nobody was emailed. Log them as Blocked with a reason. | `server/notify.ts:216` |
| E10 | Low | **Smaller retry and timing details.** <br>• `mail.retried` is audited even when nothing was attempted. <br>• The interim key is fixed to version 1, so results completed after added Validation are not emailed again. <br>• All rows of one change share its start time, so the 10-minute "stale" clock starts early for late rows. | `app/api/admin/mail/route.ts:38`, `server/notify.ts` |

**Checked and found correct:**
- **Graph token and sendMail:** the client-credentials token request, the token cache, and the `sendMail` request shape with `saveToSentItems` are right, and 202 is the only success.
- **Outcome rules:** a timeout or 500/502/504 is Outcome unknown, and 401/403/404/429 are Failed.
- **Exactly once:**
  - Each message has a unique dedupe key, so a race sends only once.
  - The retry claim is guarded.
  - The Sent Items confirmation is enforced by the server (409 without it).
  - Blocked rows cannot be retried, and the allow-list is checked again at send time.
- **Content:**
  - Every HTML value is escaped, and links use `APP_ORIGIN` only.
  - Graph's JSON API rules out header injection.
  - Client emails carry no staff names, comments or links.
  - The invitation token is never stored or logged.
- **Recipients:** the person who acted is excluded, and inactive accounts are skipped.
- **Oman dates:** 19:59:59Z falls on the 27th and 20:00Z on the 28th, including the year change.
- **Final report email:** a reopened job sends a new email only for a new report version.
